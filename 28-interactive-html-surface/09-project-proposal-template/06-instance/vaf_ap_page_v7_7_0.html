Abstract

This proposal defines a capstone project for the Computer Engineering department of İstanbul Kültür Üniversitesi. The project specifies an agentic software pipeline that harvests open-source Python code, analyses it with the deterministic detection calculi of the Variant Algebra Framework (VAF) [2], clusters the analysed units into variant sets, obtains from the framework's own enumerator the combinations that the algebra admits, and synthesises a running application from one admissible combination. The claim the project sets out to test is that assembly governed by the algebra yields more correct and more reproducible results than unguided generation by a language model. The framework itself is consumed as an external dependency and is not modified by the project. The plan is maintained as a validated register under the Backlog and Roadmap Semantic Framework (BRSF), and every quantitative statement in this document is generated from that register rather than typed: 7 scope areas, 14 goals, 14 objectives, 25 work items in 5 roadmap packages, 6 iterations and 3 milestones. The document is organised so that the body reads as a conventional proposal, while the register, the ontology alignment and the lineage evidence are placed in the appendices.

1. Executive Summary

The project addresses a long-standing gap between the abundance of tested open-source code and the absence of a reliable method for composing it with formal guarantees. The proposed system replaces ad hoc copy-and-adapt reuse with composition that is admitted or refused by an algebra, so that every assembled application can be traced back to the operators that permitted it. The algebra is the Variant Algebra Framework, first formalised in the advisor's doctoral thesis [1] and now maintained as a live repository that has materially outgrown the thesis [2].

The project is deliberately a consumer of that framework. The register records the framework as an external dependency owned by its maintainer, with 3 enhancement proposals filed in the framework's own inbox and 13 of the 25 work items carrying an explicit dependency edge on it. What the project builds is the pipeline around the framework: five agents that pass work to one another through handoffs validated by the Shapes Constraint Language (SHACL) [4], a corpus index, a human review gate for any decision that rests on a probabilistic calculus, and an evaluation that compares algebra-governed assembly with unguided generation and is required to report the case in which the algebra performs worse.

The plan is complete and validates with zero violations against the current BRSF shapes, but no work has begun: all 25 work items are in the Proposed state and no planning event has been recorded. The project is intended to be developed by a student team, and this document is the baseline against which that team will be assessed at close.

2. Introduction and Problem Context

2.1 Current State

Software teams that assemble variant-based systems currently rely on manual component selection or on copy-and-adapt reuse. Code search returns candidates without any formal classification of what they are or how they may be combined, and code generators based on language models produce outputs whose admissibility cannot be checked algebraically. The open-source ecosystem therefore contains a large body of tested code that goes unused, because the mechanisms that would discover, classify and compose it with a correctness argument do not exist in practice. The software product line community has long argued that systematic variation requires an explicit model of commonality and variability [8]; what has been missing is a computable algebra over real, harvested units and an agentic process that applies it.

2.2 Desired State

In the desired state a practitioner states a mission, and the pipeline discovers pre-tested open-source units, records for every detected dependency which of the framework's calculi produced it, clusters the units into variant sets, obtains the admissible compositions from the framework's enumerator, synthesises an executable artefact from one of them, executes it in the framework's sandbox and gates it against the framework's quality policy. Any operator whose provenance traces to a probabilistic calculus passes a human review gate that has itself been shown to refuse a known-bad input. The gap between the two states, mapped onto the register's scope deliverables, is summarised in Table 1.

2.3 Relationship to the Framework

The distinction between the thesis and the repository matters for the project's claims. The thesis is the original formal basis of the algebra [1]. The repository is the working source: at release 2.0.0 with ontology 3.2.6 it declares sixteen operator classes, nine executable detection calculi and a runtime with a variant domain-specific language (DSL), an enumerator and synthesis backends [2]. Every figure about the framework in this proposal was re-derived from the repository's bytes on 2026-09-09, and the two sources are cited separately so that a reader can tell which is being relied upon.

3. Mission

Replace ad hoc software reuse with algebraically governed, domain-aware, formally verified clean reuse, grounded in the Variant Algebra Framework published at altunelyusuf/VAF.

The mission is recorded in the register as owner-stated and carries a correction note: an earlier proposal grounded the mission in the thesis alone, whereas the live framework is what the project builds on. The mission is the root of the intent chain from which the scope, the goals and the objectives are derived, and it is quotable as the criterion against which the project will be judged at close.

8. Methodology

8.1 Algebraic Grounding

The framework's ontology declares sixteen distinct subclasses of its operator class, fifteen of them leaves, in four families: variability operators (mandatory, optional, exclusive, or, dependency and repetition), algebraic operators (addition, subtraction, Cartesian product, division and inverse), a structural composition operator whose ontology source cites the Fractal component model [9], and an intersection operator added in ontology version 3.2.0 and therefore absent from the thesis. Nine detection calculi are declared as individuals with tested implementations behind them. Four semantic marker calculi exist as tested runtime code but are not declared as individuals in the ontology; that asymmetry constrains the design, because the similarity agent cannot reference them by identifier without inventing one, and 4 of the 7 recorded coverage gaps trace to it. The operator families, the calculi and the alignment between the project's concepts and the framework's are tabulated in Appendix C.

8.2 Alignment Rather Than Import

The project's terminology box (TBox) declares only the project's own concepts, namely five agents, the pipeline, the handoffs between agents, the corpus index and the human review requirement. Each concept carries a close-match link to the framework class whose machinery it drives, and the framework is never imported, because importing it would pull its entire software-specific vocabulary into a model that uses only part of it. The alignment follows the cite-not-import pattern already established in the ecosystem and is listed in Appendix C.

8.3 What the Algebra Does Not Decide

The framework's operators determine which combinations of harvested units are algebraically admissible. They determine nothing about whether an admissible variant satisfies the mission, whether interface glue authored by a language model is correct, or whether the assembled application is fit for purpose. Those judgements remain the project's responsibility and are discharged through SHACL-gated handoffs, the framework's quality policy, sandbox execution and the human review gate. The boundary is recorded formally in the project's ontology as a named individual rather than left as prose.

8.4 Proof That the Framework Is Used

An integration probe shipped with the package loads the framework's enumerator, builds a component from the framework's own types, and checks both that a combination breaking an exclusion rule is refused and that a combination respecting it is allowed; a probe that checked only the refusal would pass against an algebra that refused everything. Six of six checks hold at the framework commit recorded in Appendix D. The probe also found that the framework's enumerator cannot be imported without the lark package, which the framework does not declare; that finding became a work item on this side and a proposal on the framework's side.

8.5 Research and Development Method

The mission makes an empirical claim, so the project follows a design-science method: build the artefact, then measure it against a baseline through the evaluation work items, which may find against the claim. Development proceeds in 6 iterations whose duration follows the course's two-week reporting cadence; each iteration's goal is stated in terms of what the framework must do by its end. The plan itself is governed by the BRSF, under the Ontology Engineering (OE) Operating Discipline and the Lineage Operating Discipline, both of which are resolved by highest version at the start of every working session. Multi-agent software development frameworks such as MetaGPT [6] and recent work on specifying human-agent boundaries in the development lifecycle [7] motivate the choice to make handoffs and review gates explicit rather than leaving them to prompts.

20. Conclusion

This proposal commits a student team to a bounded scope, 14 goals with named metrics, 14 objectives with baselines and targets, and 25 work items delivered in 5 packages across 6 iterations, all of which are held in a validated register from which this document is generated. The framework the project depends on is declared as what it is, an external dependency that the project consumes and proposes changes to but does not modify. This project does not own the variant algebra framework and cannot change it by deciding to. It is released separately, versioned separately, and maintained in a separate session. Everything this project claims about formal correctness rests on it. Two things this project needs are currently missing from it, and neither can be fixed from this side: the framework declares the classes for quality and execution reporting but no property connecting them, and its four semantic marker calculi exist as tested code with no identity in its ontology. Both are the subject of proposals below. The version relied upon is release 2.0.0, ontology 3.2.6.

13 work items depend on it: Cluster discovered features into VariantSets; Declare the packages the framework needs in order to run; Compare algebra-governed assembly against unguided generation; Fail the build when the framework changes in a way this project relies on; Harvest the corpus and run C1-C9 over it; Run the framework's nine detection calculi over the harvested code; Call the framework's enumerator to produce the admissible variants; Enumerate admissible variants under the VAF operator algebra; Pin the variant algebra framework to a known version; Gate synthesis on QualityPolicy and sandbox execution; Assemble and synthesise the deployable artefact; Test that the algebra actually refuses the combinations it should; Enforce the Tier-5 human review gate at the handoff. 2 work items are blocked on an upstream change: Cluster discovered features into VariantSets; Gate synthesis on QualityPolicy and sandbox execution.
