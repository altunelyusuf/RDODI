DigitalSignature

asymmetric

A digital signature is a cryptographic scheme that lets a signer bind their identity to a message using a private key. A verifier checks the signature against the signer's public key, confirming both authenticity (who signed it) and integrity (it was not altered). Common schemes include RSA-PSS and ECDSA, both standardized and widely deployed in TLS certificates and code signing. [Author, 2026]

Definition

A digital signature is a cryptographic scheme that lets a signer bind their identity to a message using a private key, producing a value a verifier can check against the signer's public key. Unlike a handwritten signature, it is mathematically bound to the exact bytes signed, so any alteration afterward invalidates it.

Mechanism

The signer computes a cryptographic hash of the message first, then encrypts that hash with their private key -- signing the full message directly would be far slower and is never done beyond trivial payloads. A verifier recomputes the hash independently and compares it against the decrypted signature value; any mismatch, even one flipped bit, invalidates the signature.

Variants

RSA-PSS derives its security from the difficulty of factoring large composite numbers, typically using 2048-4096 bit keys. ECDSA achieves comparable security with far smaller keys (256 bits is common) via the elliptic-curve discrete-logarithm problem. EdDSA, built on Edwards curves, avoids implementation pitfalls (nonce reuse) that have caused real ECDSA key-recovery failures.

History

RSA (1977) was the first practical public-key signature scheme, following Diffie and Hellman's 1976 conceptual proposal of public-key cryptography. DSA followed in 1991 as a US federal standard; ECDSA, its elliptic-curve variant, became widely deployed after 2000 as curve-based cryptography matured and offered smaller keys for equivalent security.

Standards

FIPS 186-5 (2023) is the current US federal standard specifying DSA, ECDSA, and EdDSA parameters. RFC 8032 standardizes EdDSA (Ed25519/Ed448) for interoperable implementation. X.509, the certificate format underlying TLS, embeds a digital signature from the issuing certificate authority in every certificate it issues.

Security

A weak or reused random nonce during ECDSA signing can leak the entire private key from just two signatures -- not theoretical; it caused the 2010 Sony PS3 signing-key leak. Signature malleability, where a second valid signature can be produced for the same message without the private key, has broken systems assuming signature uniqueness for deduplication.

Usage

TLS certificates are signed by certificate authorities, forming the trust chain browsers use to verify website identity without prior contact. Code-signing certificates let operating systems verify installed software hasn't been tampered with since publishing. Blockchain systems use signatures to prove transaction authorization without a central authority.

Comparison

Compared to a Message Authentication Code (MAC), a digital signature provides non-repudiation -- a third party can verify who signed something, since verification uses a PUBLIC key, whereas MAC verification requires the SAME shared secret used to create it, so anyone who can verify a MAC could also have forged it.

Common Misconception

A common misconception is that a digital signature ENCRYPTS the message -- it does not; the message can remain fully readable. The signature is a separate value proving authenticity and integrity, appended to (or alongside) the plaintext message.

Non-repudiationthe property that a signer cannot later deny having signed, since only their private key could have produced a valid signature.

HashFunction

hash

A cryptographic hash function maps an input of arbitrary length to a fixed-size digest, such that finding two different inputs with the same digest is computationally infeasible. Hash functions underlie integrity checks, password storage (combined with salting), and digital signatures, since signing a short digest is far cheaper than signing an entire message. SHA-256, part of the SHA-2 family, remains a standard choice; the older MD5 and SHA-1 are considered broken for collision resistance. [Author, 2026]

Definition

A cryptographic hash function maps an input of arbitrary length to a fixed-size digest, such that finding two different inputs with the same digest is computationally infeasible. Hash functions underlie integrity checks, password storage, and digital signatures.

Mechanism

SHA-256 processes input in 512-bit blocks through 64 rounds of a compression function, producing a 256-bit digest. The 'avalanche effect' -- flipping one input bit changes roughly half the output bits -- is a deliberate design property, verified statistically during standardization, that makes the digest behave unpredictably under small input changes.

Variants

SHA-2 (SHA-256, SHA-512) remains the dominant family in current deployment. SHA-3, standardized in 2015, uses a fundamentally different internal structure (a sponge construction) as a hedge against any future structural weakness discovered in SHA-2. BLAKE2/BLAKE3 offer comparable security with significantly better software performance.

History

MD5 (1992) and SHA-1 (1995) were the dominant hash functions for over a decade. Both are now considered broken for collision resistance -- researchers demonstrated a practical SHA-1 collision in 2017 (the 'SHAttered' attack), and MD5 collisions have been practical since 2004. SHA-2 (2001) remains unbroken as of 2026.

Standards

FIPS 180-4 specifies the SHA-2 family. FIPS 202 specifies SHA-3. NIST ran an open, multi-year public competition (2007-2012) to select SHA-3's Keccak algorithm, modeled on the successful AES selection process, specifically to build public confidence after the SHA-1 weaknesses emerged.

Security

Hash functions have three required properties: preimage resistance (can't find an input for a given output), second-preimage resistance (can't find a different input matching a given input's output), and collision resistance (can't find any two inputs with the same output) -- these are progressively easier to break, which is why collision-resistance failures (like SHA-1's) are taken seriously even when preimage resistance still holds.

Usage

Git uses SHA-1 (transitioning to SHA-256) to identify every commit and file by content hash. Password storage systems hash passwords (with salting and deliberate slowness via bcrypt/Argon2) rather than storing them directly. Blockchain systems use hash functions both for block linking and as the basis of proof-of-work mining.

Comparison

Compared to a checksum like CRC32, a cryptographic hash function is specifically designed to resist DELIBERATE tampering -- CRC32 is fast and good at detecting accidental corruption but trivially reversible/forgeable by an adversary, making it unsuitable for any security-relevant integrity check.

Common Misconception

A common misconception is that a longer hash output is always 'more secure' in a way proportional to its length -- security depends on the algorithm's actual cryptanalytic resistance, not output length alone; a broken 512-bit hash (like some MD variants) is not safer than an unbroken 256-bit one.

Protocols

protocol

Cryptographic protocols are structured sequences of messages that combine primitives -- hashing, signing, key exchange -- into a coherent, secure interaction. A protocol's security depends not just on its individual primitives but on how they are sequenced and what assumptions each step makes about the other party. TLS, SSH, and Signal's double-ratchet are all protocols built from broadly similar cryptographic primitives, arranged very differently. [Author, 2026]

Definition

Cryptographic protocols are structured sequences of messages that combine primitives -- hashing, signing, key exchange -- into a coherent, secure interaction. A protocol's security depends not just on its primitives but on how they are sequenced and what assumptions each step makes about the other party.

Mechanism

A protocol typically interleaves authentication (proving identity), key agreement (deriving a shared secret), and integrity protection (detecting tampering) across multiple message round trips, with each step's output feeding the next -- an attacker who can reorder, replay, or drop specific messages can sometimes break a protocol even when every individual cryptographic primitive it uses remains unbroken.

Variants

TLS, SSH, and Signal's double-ratchet protocol are all built from broadly similar primitives (asymmetric key exchange, symmetric encryption, MACs/signatures) arranged very differently to satisfy different threat models -- TLS optimizes for one-shot connection setup, SSH for interactive sessions, and Signal specifically for forward secrecy even if a long-term key is later compromised.

History

The Needham-Schroeder protocol (1978) was an early formal authentication protocol; Gavin Lowe's 1995 discovery of a man-in-the-middle flaw in its public-key variant, found via automated formal verification (the FDR model checker), became a landmark demonstration that protocol logic errors can persist for years even in well-studied designs.

Standards

IETF RFCs specify most widely deployed protocols (TLS, SSH, IPsec). Formal verification frameworks like ProVerif and Tamarin are increasingly used to machine-check protocol security properties before standardization, following the Needham-Schroeder lesson that manual review alone is insufficient for protocols of real complexity.

Security

Protocol-level vulnerabilities are frequently NOT breaks of the underlying cryptography at all -- they are logic errors: missing a check, accepting a downgraded version, or reusing a value across contexts where it shouldn't be reused. This is why protocol design is typically formally verified via symbolic model checking rather than assembled ad hoc from individually-secure primitives.

Usage

Every secure network interaction -- browsing HTTPS sites, SSH-ing into a server, sending an end-to-end-encrypted message -- relies on a cryptographic protocol correctly sequencing primitives. Financial systems (EMV chip cards) and government systems alike depend on formally analyzed protocols for their security guarantees.

Comparison

Compared to a bare cryptographic primitive (a cipher or hash function in isolation), a protocol's security is a claim about an entire MULTI-PARTY INTERACTION over an untrusted network, which is why protocol security proofs are structurally different from primitive security proofs -- they must account for an active adversary who controls the network, not just one who observes ciphertext.

Common Misconception

A common misconception is that using 'proven' primitives (AES, RSA) automatically makes a custom protocol secure -- protocol security is a separate, additional property that must be independently analyzed; secure primitives assembled incorrectly routinely produce insecure protocols.

Related: see TLS and DigitalSignature for concrete protocol examples.

PublicKey

asymmetric

A public key is the openly shared half of an asymmetric key pair, paired with a private key the owner keeps secret. Data encrypted with a public key can only be decrypted with its matching private key, and signatures made with a private key can be verified with the public key. This asymmetry is what lets two parties who have never met establish secure communication or verify authenticity. [Author, 2026]

Definition

A public key is the openly shared half of an asymmetric key pair, paired with a private key the owner keeps secret. Data encrypted with a public key can only be decrypted with its matching private key, and signatures made with a private key can be verified with the public key.

Mechanism

The security of public-key cryptography rests on a computational asymmetry: operations like modular exponentiation (RSA) or elliptic-curve point multiplication (ECC) are cheap to compute forward but currently infeasible to invert without the private key -- this asymmetry, not secrecy of the algorithm, is the whole basis of security.

Variants

RSA keys (2048+ bits) rely on integer factorization hardness. Elliptic-curve keys (256 bits typical) rely on the discrete-logarithm problem over elliptic curves, achieving comparable security with far smaller keys. Post-quantum candidates (lattice-based, e.g. Kyber) are being standardized because both RSA and ECC are vulnerable to a sufficiently large quantum computer running Shor's algorithm.

History

Diffie and Hellman's 1976 paper 'New Directions in Cryptography' first proposed public-key cryptography conceptually, though without a working encryption scheme. RSA (1977) supplied the first practical implementation. GCHQ's Clifford Cocks had independently discovered an equivalent scheme in 1973, but it remained classified until 1997.

Standards

PKCS#1 specifies RSA encryption and signature padding schemes. X.509 defines the certificate format binding a public key to an identity, verified by a certificate authority's signature. RFC 7748 standardizes Curve25519 and Curve448 for elliptic-curve key exchange.

Security

A public key alone reveals nothing about the private key under current cryptanalysis, but the BINDING between a public key and an identity is the actual attack surface -- a certificate authority that issues a certificate for the wrong identity, or a user who accepts an unverified key, defeats the whole system regardless of how strong the underlying math is.

Usage

HTTPS relies on the server's public key (in its certificate) to establish an encrypted session. SSH uses public-key pairs for both server authentication and, optionally, passwordless client login. PGP/GPG email encryption lets senders encrypt to a recipient's published public key without prior key exchange.

Comparison

Compared to a symmetric key, a public key needs no secure channel to distribute -- it can be published openly -- but public-key operations are orders of magnitude slower computationally, which is why real protocols (TLS) use public-key crypto only to exchange a symmetric session key, then switch to symmetric encryption for the bulk data.

Common Misconception

A common misconception is that the public key must be kept secret like the private key -- the opposite is true: the public key's usefulness depends entirely on it being widely and openly distributed, so anyone can verify signatures or encrypt messages to the owner.

Case: HTTPS trust chain

Every browser ships a list of trusted certificate-authority public keys; a website's certificate is verified by checking its signature against one of these roots.

SymmetricCipher

symmetric

A symmetric cipher uses the same secret key for both encryption and decryption, making it fast enough for bulk data but requiring the key to be shared securely beforehand. AES (Advanced Encryption Standard) is the dominant symmetric cipher today, typically used with 128- or 256-bit keys in an authenticated mode such as GCM. Because the same key does both directions, symmetric ciphers are usually combined with an asymmetric scheme just to exchange that key safely. [Author, 2026]

Definition

A symmetric cipher uses the same secret key for both encryption and decryption, making it fast enough for bulk data but requiring the key to be shared securely beforehand. AES (Advanced Encryption Standard) is the dominant symmetric cipher today.

Mechanism

AES operates on fixed 128-bit blocks regardless of key length; 128/192/256-bit keys control the number of internal transformation rounds (10/12/14 respectively), not the block size. Each round applies substitution, permutation, and key-mixing steps designed so that no efficient mathematical shortcut is known to skip the full round sequence.

Variants

Block cipher MODES determine how AES's fixed-block operation extends to arbitrary-length messages: ECB (insecure, patterns leak), CBC (needs a random IV, no built-in authentication), and GCM (combines encryption with authentication, the modern default) each have very different security properties despite using the identical underlying cipher.

History

DES (1977), with its 56-bit key, was the dominant standard for two decades until brute-force attacks became practical by the late 1990s. Triple-DES extended its life by applying DES three times. AES, selected via NIST's open 1997-2000 public competition (won by the Rijndael algorithm), replaced both in 2001 and remains unbroken.

Standards

FIPS 197 specifies AES. NIST SP 800-38D specifies GCM mode. The AES competition itself became the template later reused for the SHA-3 hash competition -- an open, adversarial public review process is now the standard path for adopting new cryptographic primitives.

Security

Encryption alone, without authentication, is now considered insufficient for most real-world use -- an attacker who can't read encrypted data may still be able to flip bits and cause predictable changes in the decrypted output (a malleability attack), which is exactly what authenticated modes like GCM are designed to prevent by rejecting any tampered ciphertext outright.

Usage

Disk encryption (BitLocker, FileVault, LUKS) uses AES to protect data at rest. TLS uses AES-GCM as its default symmetric cipher for the bulk of a connection after the handshake. Wi-Fi security (WPA2/WPA3) uses AES in CCMP mode to encrypt wireless traffic.

Comparison

Compared to an asymmetric cipher like RSA, AES is orders of magnitude faster and has no message-length overhead from key size, which is exactly why real protocols use asymmetric crypto only to exchange a symmetric key, then switch to a symmetric cipher for the actual data.

Common Misconception

A common misconception is that AES-256 is meaningfully 'more secure' than AES-128 against realistic attacks -- both remain far beyond any known practical brute-force attack; the difference matters mainly for long-term post-quantum margin, not near-term risk.

TLS

protocol

Transport Layer Security is the protocol that secures the great majority of web traffic, sitting between the application layer and the transport layer. A TLS handshake negotiates a cipher suite, authenticates the server (and optionally the client) via certificates, and derives session keys for symmetric encryption of the actual data. Modern deployments (TLS 1.3) reduced handshake round trips and removed several legacy cipher options that had known weaknesses. [Author, 2026]

Definition

Transport Layer Security is the protocol securing the great majority of web traffic, sitting between the application layer and the transport layer. A TLS handshake negotiates a cipher suite, authenticates the server (and optionally the client) via certificates, and derives session keys for symmetric encryption of the actual data.

Mechanism

The client and server exchange random values and negotiate parameters, the server proves its identity via a certificate signed by a trusted authority, both sides derive a shared secret via a key-exchange algorithm (commonly elliptic-curve Diffie-Hellman), and that secret seeds symmetric session keys used for the remainder of the connection.

Variants

TLS 1.3 (2018) reduced the handshake to a single round trip in the common case, down from two in TLS 1.2, and removed several legacy cipher options with known weaknesses (RC4, static RSA key exchange, CBC-mode ciphers without proper padding checks). Earlier SSL versions (2.0, 3.0) are now considered fully broken and disabled in modern browsers.

History

SSL 1.0 (Netscape, 1994) was never publicly released due to security flaws; SSL 2.0 followed in 1995, then SSL 3.0 in 1996. TLS 1.0 (1999) was effectively SSL 3.1, standardized by the IETF. The POODLE (2014) and BEAST (2011) attacks against SSL 3.0 and TLS 1.0/1.1 drove the industry-wide push to TLS 1.2 and later 1.3.

Standards

RFC 8446 specifies TLS 1.3. The IETF's TLS working group maintains the protocol; cipher suites, extensions, and certificate formats are each separately standardized (RFC 8447 registers TLS parameters). The CA/Browser Forum sets baseline requirements certificate authorities must follow to be trusted by major browsers.

Security

Certificate validation failures -- expired certificates, mismatched hostnames, untrusted issuers -- are the most common real-world TLS failure mode, not cryptographic breaks of the protocol itself. Downgrade attacks, where an attacker forces negotiation to a weaker, vulnerable version, motivated TLS 1.3's removal of legacy fallback mechanisms entirely.

Usage

Every HTTPS website uses TLS to encrypt traffic between browser and server. Email protocols (SMTP, IMAP) commonly wrap connections in TLS (STARTTLS) for transport security. VPN protocols and many internal microservice architectures use TLS or its datagram variant DTLS for service-to-service encryption.

Comparison

Compared to IPsec, TLS operates at the application/transport boundary and is application-aware (a browser explicitly negotiates it), while IPsec operates at the network layer and is transparent to applications -- this is why TLS is the default choice for securing individual web connections, while IPsec is more common for site-to-site VPN tunnels.

Common Misconception

A common misconception is that TLS alone guarantees a website is trustworthy -- it only guarantees the CONNECTION is encrypted and the certificate's identity claim is validly signed; a certificate can be issued to a malicious domain that a browser will show as 'secure' regardless.
